# Проверки PR в ядре Hermes: что проходит наш перепин каталога

Документ описывает путь пул-реквеста в `NousResearch/hermes-agent` от открытия до мержа — на
примере нашего PR [#138527](https://github.com/NousResearch/hermes-agent/pull/138527) (перепин
записи `hermes-mobile` в каталоге плагинов). Данные сняты с живого PR 16 октября 2026.

## Коротко: три ступени до мержа

| Ступень | Кто проходит | Что проверяется | Как выглядит в PR |
|---|---|---|---|
| 1. Запуск прогонов | мейнтейнер снимает блокировку первого запуска | что PR вообще допустим к проверке | до одобрения все прогоны висят в `action_required` |
| 2. Прогоны (5 workflow, 52 проверки) | автомат репозитория | что изменение не ломает ядро и валидно для каталога | `28 ✅ / 24 ⏭`, провалов ноль |
| 3. Ревью и мерж | мейнтейнер | содержание изменения | `reviewDecision` не пуст → кнопка мержа активна |

**Ключевое:** зелёные прогоны сами PR не мержат. Пока ревью нет, GitHub держит
`mergeStateStatus = BLOCKED`, даже если все проверки прошли.

## Ступень 1. Кто-то должен разрешить прогоны

У нового контрибьютора первый запуск workflow требует одобрения мейнтейнера — это защита от
того, что чужой код начнёт исполняться на раннерах. До одобрения каждый прогон отчитывается
`completed / action_required` (работа не начиналась), а в `gh pr checks` список выглядит пустым —
именно поэтому «нет проверок» ≠ «проверки не нужны».

У нас блокировку снял мейнтейнер: 16 октября в 07:13–07:16 UTC появился лейбл **`ci-reviewed`**,
и прогоны отработали со второй попытки (`run_attempt: 2`).

## Ступень 2. Что именно прогоняется

Пять workflow на голове PR (`fb502e35…`, наш перепин):

| Workflow | Итог | Что доказывает |
|---|---|---|
| **Plugin Catalog CI** | ✅ success | запись каталога структурно валидна и пин ведёт на существующий коммит |
| **CI** | ✅ success | изменение ничего не ломает: линты, тесты Python, OS-специфика, JS/TS, Rust, документация и десятки структурных проверок |
| **Docker Build, Test, and Publish** | ✅ success | образ собирается и проходит тесты (публикация в PR не выполняется) |
| **Nix flake check** | ✅ success | сборка через Nix воспроизводима |
| **Label rerun** | `action_required` | служебный автомат репозитория (перезапуск по лейблу), к нашему коду не относится |

### Plugin Catalog CI — то, что относится к нам напрямую

Два задания, оба зелёные:

* `structural` — структура записи: обязательные поля, формат `sha`, версии, согласованность
  `tier`/`category`/`requires_hermes`;
* `pinned-source-validate` — пин указывает на реальный коммит в указанном репозитории и в
  указанном `subdir` есть манифест плагина (`plugin.yaml`), причём его `version` совпадает с
  записью каталога.

Именно эта пара проверок закрывает вопрос «запись не отставшая и не битая»: наш пин
`91bdca08…` (плагин 1.1.1) их прошёл.

### CI — большой прогон (что внутри)

`CI` — это составной workflow, который подтягивает 25 вложенных наборов проверок. Все они
завершились успешно; для понимания, что именно проверено:

* **Линты Python:** `ruff enforcement`, `ruff + ty diff`, `code health ratchet`,
  `Windows footguns` (запрет конструкций, ломающихся на Windows);
* **Тесты Python:** `Run tests (1/2)`, `Run tests (2/2)`, `Python tests / e2e`,
  `e2e-upgrade`, `e2e-upgrade-plan`;
* **Проверки под конкретные ОС:** macOS-тесты (2 части), Windows-тесты (обычные и arm64, по
  2 части), `Windows install + update E2E` — установка и обновление реальными процессами;
* **JS и Rust:** `JS & TS checks`, `Rust tests`;
* **Структурные и репозиторные:** большие бинарники, атрибуция контрибьютора, «нет
  случайных инфографик», коллизии имён файлов (регистр), общая история с базовой веткой,
  свежесть иконок, запрет production-импортов заглушки `tools.lazy_deps`, артефакты профиля,
  `prompt surface diff`, `Supply-chain scan`, удалённые терминальные бэкенды;
* **Зависимости:** `uv.lock`, `package-lock.json diff`, `lockfile-diff`;
* **Документация и сборка:** `Docs Site`, `Bootstrap installer`, `Lint Docker scripts`;
* **Десктоп:** `Desktop E2E`, `Desktop core E2E`, `Desktop update E2E` — но они относятся к
  условным шагам (см. ниже);
* **Финал:** `All required checks pass (v2)` — сводная проверка, по которой GitHub и решает,
  можно ли мержить.

### Почему часть проверок «skipped»

24 проверки из 52 помечены `⏭ skipped` — это **не** провал и не недосмотр: это условные шаги,
которые запускаются только там, где применимы (сборка и публикация docker-образа, публикация
манифеста версии, десктопные E2E, полный набор OS-тестов для релизной ветки). Для правки из
трёх строк в записи каталога они не применимы, и `skipped` — ожидаемый итог.

## Ступень 3. Ревью и мерж

Проверки зелёные, но мерж держится:

* `mergeable = MERGEABLE` — конфликтов с базовой веткой нет;
* `mergeStateStatus = BLOCKED` — осталось отсутствие ревью;
* `reviewDecision` пуст, ревью и inline-комментариев нет.

Что нужно от мейнтейнера: посмотреть диффа записи (три строки: `sha`, `version`, расширенное
`description`) и выставить ревью. После этого кнопка мержа становится доступной.

## Что это значит для нашего PR

1. Мы поменяли ровно три строки в `plugin-catalog/hermes-mobile.yaml`; ничего в коде ядра не
   трогали.
2. Содержательная часть — две проверки каталога (`structural`, `pinned-source-validate`);
   остальное доказывает, что мы не сломали ничего в ядре.
3. Пока PR не смержен, пин в проде не меняется: на `main` всё ещё `1.0.0 @ 7fdaf232…`, поэтому
   установка плагина по имени даёт 1.0.0, а не нашу 1.1.1.
4. После мержа: обновить плагин у уже установленных агентов — `hermes plugins update hermes-mobile`.

## Как посмотреть состояние самому

```bash
gh pr view 138527 --repo NousResearch/hermes-agent \
  --json state,mergeable,mergeStateStatus,reviewDecision,headRefOid
gh pr checks 138527 --repo NousResearch/hermes-agent          # список проверок головы
gh api repos/NousResearch/hermes-agent/commits/<sha>/check-runs --jq '[.check_runs[].conclusion] | group_by(.) | map("\(length) × \(.[0])")'
```

Полезно помнить: `gh pr checks` показывает только те проверки, которые уже начались. Пока
прогоны ждут одобрения, вывод будет «no checks reported» — это состояние ожидания, а не пустой
список требований.
